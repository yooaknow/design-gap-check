# 디자인 빈칸 찾기

## 이 스킬이 푸는 문제

빈 화면, 에러, 마감, 권한 없음 같은 예외 상태는 PRD에는 정책이 없고 시안에는 화면이 없는 경우가 많다. 기획자는 디자인에서 알아서 그릴 거라고, 디자이너는 기획에서 정해 줄 거라고 생각하다가 개발 단계에서 문제가 터진다.

이 스킬은 그 빈칸을 찾아서 **정해야 할 사람에게, 답하기 쉬운 형태로** 넘긴다.
- 기획자는 빈칸을 글로 채우는 대신 선택지 중 하나를 고른다.
- 디자이너는 무엇을 더 그려야 하는지 목록으로 받는다.
- 기획자가 고른 답은 PRD에 붙일 문단으로 바뀐다.

## 두 가지 모드

| 모드 | 언제 | 결과물 |
|---|---|---|
| 검수 모드 (기본) | 시안과 PRD를 받았을 때 | `templates/report.md` 형식의 빈칸 리포트 |
| 반영 모드 | 기획자가 `Q1 B, Q2 A`처럼 답을 보냈을 때 | `templates/prd-update.md` 형식의 PRD 반영 문단 |

사용자 메시지에 질문 번호와 선택지가 들어 있으면 반영 모드, 그 외에는 검수 모드로 동작한다.

## 검수 모드

### 1. 입력 확인

필요한 것:
- **시안**: Figma 링크, 스크린샷, 화면 설명 텍스트 중 하나 이상
- **PRD**: 기능 설명, 정책, 유저 스토리. 없으면 시안만으로 진행하되 정책이 필요한 빈칸은 모두 기획 질문으로 돌린다.

Figma 링크를 받았고 Figma 도구(MCP)를 쓸 수 있으면 프레임 목록과 스크린샷을 직접 읽는다. 도구가 없으면 스크린샷을 올려 달라고 요청한다.

화면이 15개를 넘으면 한 번에 다 보지 말고, 먼저 검수할 기능 흐름 하나를 고르게 한다.

### 2. 화면 목록 만들기

시안의 화면(프레임)마다 다음을 정리한다. 이 목록은 리포트에 넣지 않고 판단에만 쓴다.
- 화면 이름: 시안의 프레임 이름 그대로
- 화면 유형: `references/states-checklist.md`의 유형 중 하나 이상. 애매하면 가장 가까운 유형을 고른다.
- 이미 그려진 상태: 시안에서 실제로 확인되는 상태만 적는다.
- PRD 근거: 이 화면과 관련된 PRD 절 번호

### 3. 체크리스트와 대조

`references/states-checklist.md`를 읽고, 화면 유형별 상태와 공통 상태를 하나씩 대조한다. 각 상태를 다음 넷 중 하나로 분류한다.

| 분류 | 조건 | 리포트에서 |
|---|---|---|
| 있음 | 시안에 화면이 있고, 필요한 정책도 PRD에 있다 | 적지 않는다 |
| 기획 질문 | 무엇을 보여줄지, 어떻게 동작할지 **결정**이 필요하다 | 기획자에게 묻는 질문 |
| 디자인 할 일 | 정책은 PRD에 있거나 필요 없는데, 화면만 없다 | 디자이너 할 일 |
| 확인 필요 | 시안에 있는지 확신할 수 없다 | 확인 필요 |

분류 기준은 하나다. **"디자이너가 이 화면을 그리려면 누군가에게 물어봐야 하는가?"** 물어봐야 하면 기획 질문, 아니면 디자인 할 일이다. 로딩 표시 방식, 오류 문구 위치, 말줄임처럼 디자이너가 스스로 정할 수 있는 것은 디자인 할 일이다.

서비스와 관계없는 상태는 건너뛴다. PRD의 "범위 밖"에 있는 기능은 검사하지 않는다.

시안에 그려진 화면이 PRD와 맞지 않거나 PRD에 없는 동작을 보여주면(예: 검색어가 비어 있는데 결과 목록이 보임) 빠진 것이 아니므로 "확인 필요"로 보낸다.

### 4. 기획자 질문 작성

`references/question-guide.md`를 읽고 따른다. 핵심만 적으면:
- 질문 하나에 결정 하나
- 디자인 용어가 아니라 사용자가 겪는 상황으로 묻는다
- 선택지는 2~4개와 "직접 입력". 각 선택지에 사용자가 보게 될 모습을 한 줄로 쓴다.
- 추천 하나를 고르고 원칙 코드(H1~H10)와 이유를 한 줄로 쓴다
- 같은 결정(같은 정책)이 여러 화면에 걸리면 하나로 묶는다. 반대로 한 화면이라도 정해야 할 정책이 다르면 따로 묻는다. 예를 들어 상세 화면의 "승인 대기 중인 사람에게 보일 버튼"과 "거절된 사람이 다시 신청할 수 있는지"는 다른 결정이다.
- 영향이 큰 순서로 정렬하고 최대 10개까지. 나머지는 "다음에 볼 질문"에 한 줄씩.

### 5. 디자이너 할 일 작성

- 디자인 할 일로 분류한 상태를 적는다.
- 기획 질문마다 "답이 나오면 그릴 화면"도 적고, 관련 질문 번호를 단다. 이 줄도 디자인 할 일 개수에 센다.
- 한 화면에서 보는 사람이나 상황에 따라 달라지는 상태는 한 줄로 묶고 관련 질문 번호를 모두 적는다.
- 같은 상태가 여러 화면에 필요하면 한 줄로 묶고 화면을 모두 적는다.
- 디자이너가 읽고 바로 작업 목록으로 쓸 수 있게, 전체를 15줄 안팎으로 유지한다.

### 6. 리포트 출력

`templates/report.md` 형식을 그대로 따른다. 비어 있는 섹션은 지우지 말고 "없음"이라고 쓴다.

## 반영 모드

1. 질문 번호별로 고른 선택지를 확인한다. 답이 없는 질문은 보류로 둔다.
2. 고른 선택지를 PRD 문장("~한다" 체)으로 바꾼다. PRD의 어느 절 아래에 붙일지 정하고, 맞는 절이 없으면 새 절을 제안한다.
3. 선택지에 없던 결정을 지어내지 않는다. 고른 답과 기존 PRD에서 바로 따라 나오는 문장(예: 승인되면 참여 중인 스터디 목록에 나타난다)은 써도 된다. 어느 쪽에도 근거가 없는 결정이 필요하면 "답에서 생긴 새 질문"에 적는다.
4. 기획자가 "새 기능 필요"로 표시된 선택지를 골랐으면 그대로 반영하되, 새 절로 제안하고 범위가 늘어난다는 점을 짚는다.
5. 디자이너 할 일을 확정된 내용으로 다시 쓴다. 바뀌지 않은 할 일은 번호만, 보류된 질문에 걸린 할 일은 따로 번호만 적는다.
6. "직접 입력" 답은 그 내용을 살려 쓰고, 다른 답이나 기존 PRD와 모순되면 짚는다.
7. `templates/prd-update.md` 형식으로 출력한다.

## 지켜야 할 것

- 시안에서 직접 확인한 것과 추정한 것을 구분한다. 확신이 없으면 "확인 필요"로 보낸다. 이미 있는 화면을 빠졌다고 하는 것이 가장 나쁜 실수다.
- 시안과 PRD에 없는 새 기능을 제안하지 않는다. 빈칸을 찾는 것까지가 역할이다. 선택지에 새 기능이 필요한 안을 넣을 때는 "새 기능 필요"라고 표시하고 추천하지 않는다.
- 색, 폰트 같은 시각 취향은 다루지 않는다. 상태와 정책만 본다.
- 결과는 한국어로 쓰고, 기획자와 디자이너가 슬랙이나 노션에 그대로 붙여 넣을 수 있게 쓴다.
